# 审查规则

## 通用规则

所有 Finding 都必须附带可定位证据。

证据优先级：

1. `文件:行号`
2. 文件 + 章节/标题
3. 文件 + 字段/精确术语

无法定位时，不下结论。

只标记可能影响 Agent 理解、路由、状态一致性或执行确定性的结构问题；不要为了形式统一本身提出 Finding。

## 1. 术语一致性

### T1 — 同一概念存在多个名称
同一概念在不同文件中使用不同名称时标记。

### T2 — 同一名称表达不同概念
同一个术语在不同位置表示明显不同含义时标记。

### T3 — 历史名称残留
旧名称已经被新名称替代，但仍存在于步骤、引用、模板、Schema 或示例中时标记。

### T4 — 跨层字段命名漂移
同一数据在不同文件或结构中使用不一致字段名时标记。

## 2. 步骤边界

### S1 — 一个步骤承担多个职责
同一步骤同时执行多个明显不同的流程职责时标记。

### S2 — 跨步骤规则泄漏
一个步骤依赖另一个步骤内部定义的规则，而该规则没有形成公共契约时标记。

### S3 — 输入来源不明确
步骤使用重要输入，但没有明确其来源文件、状态字段或生产步骤时标记。

### S4 — 输出契约不明确
步骤产生重要结果，但没有明确写入位置或后续消费者时标记。

### S5 — 完成条件不明确
步骤没有清楚定义什么状态代表完成时标记。

### S6 — 同一约束重复定义
同一个会影响 Agent 执行的约束、规则或契约在多个位置独立定义时标记。

如果多个位置只是引用同一权威定义，不标记。

重点检查重复定义是否可能导致后续修改不同步、规则分叉或执行歧义。

## 3. 执行路由

### R1 — 缺少显式路由骨架
主 `SKILL.md` 缺少足以决定步骤加载、跳过、恢复和继续执行的路由契约时标记。

不要求固定使用 Markdown 表格；决策树、状态机或其他明确形式也可以。

### R2 — 分支判断隐藏在步骤内部
如果某个判断会决定另一份 step / reference 是否需要加载，但该判断只存在于已经加载的步骤内部，则标记。

决定“是否加载”的判断，应优先位于路由层。

### R3 — 加载条件不明确
步骤或引用文件存在，但没有明确何时加载时标记。

对会显著增加上下文的 step / reference，其加载条件必须能从主路由或当前步骤契约中明确得到。

### R4 — 下一步不唯一
同一状态可能进入多个后续动作，但没有明确条件或优先级时标记。

### R5 — 路由和执行混杂
同一个步骤既决定“下一步该做什么”，又执行具体业务动作，且这两类职责可以清楚分离时标记。

## 4. 状态流转

### D1 — 跨步骤数据只存在于上下文
后续步骤依赖的数据，只能从之前的对话或模型上下文中获取时标记。

### D2 — 数据生产者不明确
某个数据被消费，但无法确定由哪个步骤产生时标记。

### D3 — 数据存储位置不明确
跨步骤数据已经产生，但没有明确稳定存储位置时标记。

### D4 — 消费来源不明确
出现“使用之前结果”“根据前面选择”等描述，但没有指定准确来源时标记。

### D5 — 存在多个事实来源
同一权威状态在多个位置独立维护，但没有明确唯一事实来源时标记。

## 状态持久化原则

不要要求所有中间推理都写入文件。

只有满足以下至少一项的数据，才建议持久化：

- 后续步骤需要
- 中断恢复需要
- 多个步骤共同使用
- 必须能够确定性重新读取

局部推理、临时候选和当前步骤内的中间结果，可以只存在于当前上下文。
